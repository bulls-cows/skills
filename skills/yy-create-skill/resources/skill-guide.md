# 技能编写指南

本文档提供技能编写的完整指南，包括模板结构、命名规范、编写原则和最佳实践。

## 编写原则

### YAML Frontmatter

- 使用 `>`（折叠式）处理长描述 - 换行符转换为空格
- **禁止**将长描述放在键的同一行
- 只允许 `name` 和 `description` 两个字段，禁止添加其他字段（如 `version`、`author`、`tags` 等）

```yaml
# ❌ 错误
description: 这是一个很长的描述，超过了...

# ✅ 正确
description: >
  这是一个很长的描述，使用折叠样式。
  换行符会转换为空格。
```

### description 编写

- **结构化公式**：`<动词引导的动作>. <何时用 / 何时不用>.`
- **排除条件优先**："何时不用"是路由价值最高的信息，应写在 description 中
- **贴近本质**：排除条件必须是 AI 真实可能误触发的相邻场景；写完后自问"不写这一条 AI 真的会误触发吗"，答案为否就删除
- **独立性**：不得出现其他技能名，需要表达差异时只描述行为差异
- **简洁性**：控制在 2-3 句话内，每个限定词必须是路由决策依据
- **关注点分离**：description 负责 when/why，指令步骤负责 how

```yaml
# ❌ 弱描述（只有动作，无路由信息）
description: Review code

# ✅ 强描述（排除条件消歧）
description: >
  审查 PR 的逻辑正确性、安全风险、测试覆盖缺口。
  仅用于审查，不用于直接改代码、编写测试或执行格式化。
```

### 使用场景

必须定义明确的触发条件和不应触发的场景：

- 触发场景必须是该技能**核心要解决的问题**
- 排除场景必须是 AI **真实可能误触发**的相邻场景
- 按真实误触发概率排序：功能相邻 > 同一对象的不同操作 > 同一动词的不同对象 > 近义请求

```markdown
## 使用场景

- 用户提到"格式化代码"、"代码格式化"

不应触发：

- 用户要求直接修改或重构代码 ← 同一对象的不同操作
- 用户只是询问代码含义或工作原理 ← 近义请求但目的不同
```

### 指令

清晰的分步说明，每一步描述具体操作：

- 使用祈使语气（"做 X"），每一步只描述一个操作
- 步骤标题格式统一为 `### 步骤 N. 标题`
- 最后一步描述输出格式
- 模板中至少给出 2-3 个步骤标题骨架

### 步骤分层与执行顺序

SKILL.md 是给顺序消费指令的 AI 读的，**章节顺序 = 决策顺序 = 执行顺序**。必须满足以下三条硬规则：

1. **判断步骤与执行步骤分层**：判断/路由类步骤只输出编排语义和分支结论，不混入具体命令；所有执行动作统一下沉到执行步骤
2. **阅读顺序等于执行顺序**：所有前置动作必须直接编入对应代码块的最前面，不得用"代码块 + 后置补充说明"的形式追加前置步骤
3. **条件不过度限定**：写"仅在 X 时执行"这类限定前，反向自问"非 X 场景下真的不需要吗？"——只要副作用一致或无害，优先写成无条件前置

### 决策点显式化

将步骤中隐含的分支选择转化为明确的规则，避免模糊表述。

**核心原则：**

- 不使用"根据情况处理"、"视情况而定"等模糊表述
- 明确每个条件分支对应的具体行为
- 优先使用列表格式呈现决策逻辑；只有确实需要多列对齐对比时才使用表格

**决策分支格式：**

```markdown
**决策分支**：

- **条件 A**：执行行为 A
- **条件 B**：执行行为 B
```

**错误示例：**

```markdown
### 步骤 2. 处理错误

根据错误类型进行相应处理。
```

**正确示例：**

```markdown
### 步骤 2. 处理错误

**决策分支**：

- **语法错误**：读取错误日志，定位行号并修复
- **类型错误**：分析类型定义，补充缺失的类型声明
- **运行时错误**：检查依赖安装和配置文件
```

### 文件间一致性

当技能包含辅助文件（resources/、templates/、examples/、prompts/）时，确保各文件对同一事项的描述一致。

**一致性检查要点：**

- 步骤编号是否一致
- 章节名称是否一致
- 字段名/术语是否一致
- 规则描述是否矛盾

**检查方法：**

1. 列出所有涉及同一事项的文件位置
2. 逐项比对描述内容
3. 发现矛盾时统一修改

**常见矛盾类型：**

| 矛盾类型       | 示例                                      | 解决方案     |
| -------------- | ----------------------------------------- | ------------ |
| 步骤编号不一致 | SKILL.md 写"步骤 3"，resources 写"步骤 2" | 统一编号     |
| 术语不一致     | 一处写"lint:fix"，另一处写"lint --fix"    | 统一术语     |
| 规则矛盾       | 一处说"自动修复"，另一处说"不修复"        | 明确条件分支 |

### 安全边界

涉及敏感操作的技能，必须明确禁止行为，防止 AI 越界执行。

**安全边界编写格式：**

```markdown
## 安全边界

**禁止主动执行的命令**：

- 编译、构建、部署命令
- 删除文件命令
- 网络请求命令（除特定 API 外）
```

### 校验强度按引入阶段校准

当技能对某类条目定义检查（警告、拦截或二次确认）时，根据条目的引入阶段校准检查强度：

- **首次引入**：检查强度应高于默认，因为首次出现意味着未经先前审查
- **已接受条目**：降低或跳过重复检查，因为先前的接受意味着已经过审查

示例：Git 提交时对敏感文件的检查——新增 `.env` 文件时应警告或拦截，但修改已被仓库接受的 `.env` 文件时无需重复提醒。

### 受众意识

SKILL.md 的读者是执行技能的 AI 助手，内容应服务于完成任务，而非展示底层实现。

**核心原则：**

- **只写 AI 需要的**：SKILL.md 只应包含对 AI 执行步骤有操作或决策价值的信息
- **不罗列源文件**：不包含 AI 不会直接操作的源代码文件清单、内部模块/组件逐项列举等
- **不替代项目文档**：技能所涉及项目的内部架构细节应放在项目自身的文档中
- **需要引用代码文件时**：使用概要描述替代逐个列举（如 `src/components/` 替代列出所有 `.vue` 文件）

### 派生技能编写

当一个技能（派生技能）基于另一个技能（源技能）产生，只在部分行为上需要覆盖时，应采用薄覆盖层写法。

**核心原则：**

- **不重复源技能内容**：源技能已定义的步骤、规则、安全边界和格式规范，派生技能不再复述
- **只声明覆盖规则**：明确说明哪些行为与源技能不同，以及为什么不同
- **说明复用关系**：在描述章节用一句话说明"在 `源技能` 基础上"做了什么，并注明"未特别说明的逻辑均复用 `源技能`"
- **覆盖需有因果**：每项覆盖必须说明覆盖原因（如"因本技能无确认步骤兜底"）

**覆盖规则的编写格式：**

```markdown
### 步骤 N. 执行源技能流程（覆盖模式）

复用 `源技能名称` 的完整流程，并应用以下覆盖规则：

**XX 覆盖**：<覆盖后的行为>。<覆盖原因>。
```

**安全边界的覆盖写法：**

```markdown
## 安全边界

复用 `源技能名称` 的安全边界，并叠加以下覆盖：

- <覆盖项>（覆盖源技能的 <原策略>，<覆盖原因>）
```

## 目录结构规范

```text
skill-name/
├── SKILL.md          # 必需，技能主文件
├── scripts/          # 可选，脚本目录（可执行技能）
│   ├── Node.js 方式
│   │   ├── main.ts       # 主执行脚本
│   │   └── package.json  # 依赖配置
│   └── Python 方式
│       ├── read_pdf.py       # 主执行脚本
│       ├── pyproject.toml    # 依赖配置（推荐）
│       └── requirements.txt  # 依赖配置（兼容旧方式）
├── examples/         # 可选，示例目录
│   ├── input.md      # 输入示例
│   └── output.md     # 输出示例
├── templates/        # 可选，模板目录
│   └── example.md    # 模板文件
├── resources/        # 可选，资源目录
│   └── reference.md  # 参考文档
└── prompts/          # 可选，提示词派生产物目录
    └── skill-prompts.md  # 由 SKILL.md 派生出的系统提示词
```

### 目录说明

- `SKILL.md`：**必需**，技能主文件，定义技能名称、描述、使用场景、指令
- `scripts/`：**可选**，可执行技能需要脚本文件时使用。脚本文件命名遵循目标语言的常见约定：Node.js/TypeScript 文件优先使用 kebab-case（如 `wechat-api.ts`，入口文件可使用 `main.ts` 或 `main.js`），Python 文件优先使用 snake_case（如 `read_pdf.py`）。依赖配置放在 `scripts/package.json`（Node.js）；Python 依赖配置优先使用 `scripts/pyproject.toml`，也兼容 `scripts/requirements.txt`
- `examples/`：**可选**，技能使用方式不直观时提供示例说明
- `templates/`：**可选**，需要生成特定格式文件或模板实际内容超过 20 行时使用（计数规则：只统计实际内容行，不含空行、代码块围栏标记行、YAML frontmatter 行）
- `resources/`：**可选**，需要参考文档或素材文件时使用
- `prompts/`：**可选**，存放由 SKILL.md 派生出的系统提示词文件，默认文件为 `prompts/skill-prompts.md`；该目录是派生产物目录，不作为技能主定义来源，优先由 `yy-skill-to-prompt` 生成

## 交互设计原则

### 核心原则

- **默认策略优先**：默认采用最常见策略，仅在用户明确要求时才提供选项
- **精简引导问题**：只保留核心必要问题，避免列出过多引导问题
- **快速模式支持**：当用户使用"直接提交"、"无需确认"等关键词时，可跳过确认步骤（前提是目标、范围和默认策略已足够明确）
- **选项必须是终点**：每个选项选后直接完成动作，不存在需要额外步骤的中间态选项；需要用户输入内容时，由用户的自由表达承担

### 交互设计检查清单

- [ ] 默认策略是否覆盖 80% 以上的使用场景？
- [ ] 引导问题是否都是核心必要问题？
- [ ] 每个选项是否都是"终点"（选后直接完成动作）？

## 技能触发方式

- **自动触发**：当用户要执行的操作与技能的 description 内容相匹配时自动触发，如：`请审查这个 PR 的风险`。
- **显式调用**：当用户主动提及技能名称时触发，如：`使用 pr-risk-check 技能来审查当前分支相对于 main 分支的差异。`。

## 常见问题与解决方案

### 问题 1：技能写成知识文档

**错误做法**：写成"什么是技能"、"技能的优点"等知识文档。

**正确做法**：SKILL.md 必须包含 `## 指令` 章节，定义可执行的步骤。

### 问题 2：负例不贴近本质或引用其他技能

**错误做法**：

- 缺少负例
- 负例是"正确的废话"（如"不用于造房子"）
- 负例引用其他技能名（如"使用 yy-edit-code"）

**正确做法**：负例必须是 AI 真实可能误触发的相邻场景，只描述行为差异，不点名其他技能。

### 问题 3：指令不清晰

**错误做法**：写"根据情况处理"等模糊表述。

**正确做法**：使用 `### 步骤 N. 标题` 格式，每步描述具体操作。

### 问题 4：决策点模糊

**错误做法**：写"执行命令并根据结果处理"。

**正确做法**：明确条件与对应行为，如"exit code 为 0 → 通过，非 0 → 分析错误"。

## 验收清单

### 通用检查项

1. `## 描述` 章节准确反映技能用途
2. description 遵循结构化公式，包含排除条件，不会误触发
3. 使用场景明确（触发条件和不应触发场景），贴近技能本质
4. 指令步骤完整可执行，最后一步描述输出格式
5. YAML 格式正确（仅 `name` 和 `description` 两个字段）
6. 决策点显式化，步骤分层清晰（判断步骤不混入执行细节）
7. 文件间一致性（SKILL.md 与辅助文件描述一致）
8. 能力一致性（适用场景有执行路径，不适用场景与指令无交集）
9. 受众意识（不罗列底层实现细节）
10. 条件未过度限定（每个限定都有清晰论据）

### 创建技能后检查项

1. 文件命名符合规范（kebab-case），使用中文描述
2. 代码示例包含语言标签
3. 目录名称合规（`scripts/`、`examples/`、`templates/`、`resources/`、`prompts/`）
4. SKILL.md 包含执行步骤，不是纯知识文档
5. 未内嵌过长模板代码（超过 20 行应移至 templates/）
6. 如有脚本文件，命名和依赖配置符合规范
7. 提示词派生产物处理符合规则（优先由 `yy-skill-to-prompt` 生成）

### 更新技能后检查项

1. description 未混入执行细节
2. 辅助文件是否需要同步更新
3. 提示词派生产物是否需要重新生成

## 质量要求

- **长度控制**：单个文件不超过 500 行，超过 300 行时考虑是否需要拆分或精简；优先精简语言减少行数，其次才拆文件
- **语言风格**：使用祈使语气（"做 X"），使用中文描述
- **代码示例**：包含语言标签

## 路径格式规范

- 使用正斜杠作为路径分隔符，路径包含空格时使用引号包裹，以确保跨平台兼容性和正确解析
