# 技能编写指南

本文档提供技能编写的完整指南，包括模板结构、命名规范、编写原则和最佳实践。

## 编写原则

### YAML Frontmatter

**关键规则：**

- 使用 `>`（折叠式）处理长段落 - 换行符转换为空格
- 使用 `|`（保留式）处理代码块或列表 - 保留换行符
- **禁止**将长描述放在键的同一行

```yaml
# ❌ 错误 - 可能导致解析错误
description: 这是一个很长的描述，超过了...
```

```yaml
# ✅ 正确
description: >
  这是一个很长的描述，使用折叠样式。
  换行符会转换为空格。
```

### description 编写

- **结构化公式**：`<动词引导的动作>. <何时用 / 何时不用>.`
- **精确性**：明确定义技能的单一任务边界
- **排除条件优先**："何时不用"是路由价值最高的信息——它能阻止误触发，也能在功能相近的技能间消歧；排除条件应写在 description 中，而非仅写在"使用场景"章节
- **简洁性**：控制在 2-3 句话内
- **必要性**：每个限定词必须是路由决策依据，不用来修饰触发例子；如果去掉某词不影响路由判断，则不应存在
- **关注点分离**：description 负责 when/why，指令步骤负责 how；如果 description 开始解释"怎么做"，说明写宽了
- **完整性检验**：读完 description 后是否还需追问"这个技能到底什么时候该用"——如果需要，则不够完整

```yaml
# ❌ 弱描述（只有动作，无路由信息）
description: Review code
```

```yaml
# ❌ 含非路由限定词（"简短"修饰例子，去掉不影响路由判断）
description: >
  帮助用户提交代码。当用户说"提交一下"这类简短表达时触发。
```

```yaml
# ✅ 精确（限定词是路由区分条件）
description: >
  审查 PR 的逻辑正确性、安全风险、测试覆盖缺口。
  仅用于审查，不用于直接改代码。
```

```yaml
# ✅ 强描述（排除条件消歧，区分功能相近技能）
description: >
  审查 PR 的逻辑正确性、安全风险、测试覆盖缺口。
  仅用于审查，不用于直接改代码、编写测试或执行格式化。
```

### 使用场景

必须定义明确的触发条件和不应触发的场景：

- 列出应该触发的典型场景
- 列出不应触发的典型场景
- 帮助 AI 理解技能边界

```markdown
## 使用场景

- 用户提到"格式化代码"、"代码格式化"
- 用户要在提交前整理代码格式

不应触发：

- 用户只是查看代码
- 用户要求重构代码逻辑
```

### 指令

清晰的分步说明，每一步描述具体操作：

- 使用祈使语气（"做 X"）
- 每一步只描述一个操作
- 最后一步描述输出格式
- 步骤标题格式统一为 `### 步骤 N. 标题`（如 `### 步骤 1. 获取改动文件列表`）
- 模板中至少给出 2-3 个步骤标题骨架，避免只写成笼统段落或普通编号列表

```markdown
## 指令

### 步骤 1. 检测项目使用的语言和格式化工具

### 步骤 2. 运行相应的格式化命令

### 步骤 3. 输出格式化结果：工具名称、处理文件数、变更摘要
```

### 决策点显式化

将步骤中隐含的分支选择转化为明确的规则，避免模糊表述。

**核心原则：**

- 不使用"根据情况处理"、"视情况而定"等模糊表述
- 明确每个条件分支对应的具体行为
- 优先使用列表格式呈现决策逻辑；只有确实需要多列对齐对比时才使用表格

**决策分支格式：**

```markdown
**决策分支**：

- **条件 A**：执行行为 A
- **条件 B**：执行行为 B
```

**错误示例：**

```markdown
### 步骤 2. 处理错误

根据错误类型进行相应处理。
```

**正确示例：**

```markdown
### 步骤 2. 处理错误

**决策分支**：

- **语法错误**：读取错误日志，定位行号并修复
- **类型错误**：分析类型定义，补充缺失的类型声明
- **运行时错误**：检查依赖安装和配置文件
```

### 文件间一致性

当技能包含辅助文件（resources/、templates/、examples/、prompts/）时，确保各文件对同一事项的描述一致。

**一致性检查要点：**

- 步骤编号是否一致
- 章节名称是否一致
- 字段名/术语是否一致
- 规则描述是否矛盾

**检查方法：**

1. 列出所有涉及同一事项的文件位置
2. 逐项比对描述内容
3. 发现矛盾时统一修改

**常见矛盾类型：**

| 矛盾类型       | 示例                                      | 解决方案     |
| -------------- | ----------------------------------------- | ------------ |
| 步骤编号不一致 | SKILL.md 写"步骤 3"，resources 写"步骤 2" | 统一编号     |
| 术语不一致     | 一处写"lint:fix"，另一处写"lint --fix"    | 统一术语     |
| 规则矛盾       | 一处说"自动修复"，另一处说"不修复"        | 明确条件分支 |

### 安全边界

涉及敏感操作的技能，必须明确禁止行为，防止 AI 越界执行。

**安全边界编写格式：**

```markdown
## 安全边界

**禁止主动执行的命令**：

- 编译、构建、部署命令
- 删除文件命令
- 网络请求命令（除特定 API 外）
```

### 校验强度按引入阶段校准

当技能对某类条目定义检查（警告、拦截或二次确认）时，根据条目的引入阶段校准检查强度：

- **首次引入**：检查强度应高于默认，因为首次出现意味着未经先前审查
- **已接受条目**：降低或跳过重复检查，因为先前的接受意味着已经过审查

示例：Git 提交时对敏感文件的检查——新增 `.env` 文件时应警告或拦截，但修改已被仓库接受的 `.env` 文件时无需重复提醒。

### 受众意识

SKILL.md 的读者是执行技能的 AI 助手，内容应服务于完成任务，而非展示底层实现。

**核心原则：**

- **只写 AI 需要的**：SKILL.md 只应包含对 AI 执行步骤有操作或决策价值的信息
- **不罗列源文件**：不包含 AI 不会直接操作的源代码文件清单、内部模块/组件逐项列举等
- **不替代项目文档**：技能所涉及项目的内部架构细节应放在项目自身的文档中
- **需要引用代码文件时**：使用概要描述替代逐个列举（如 `src/components/` 替代列出所有 `.vue` 文件）

### 派生技能编写

当一个技能（派生技能）基于另一个技能（源技能）产生，只在部分行为上需要覆盖时，应采用薄覆盖层写法，避免重复源技能已有内容。

**适用条件：**

- 派生技能的核心流程与源技能一致，仅少数步骤的行为需要覆盖
- 用户同时安装了源技能和派生技能

**核心原则：**

- **不重复源技能内容**：源技能已定义的步骤、规则、安全边界和格式规范，派生技能不再复述
- **只声明覆盖规则**：明确说明哪些行为与源技能不同，以及为什么不同
- **说明复用关系**：在描述章节用一句话说明"在 `源技能` 基础上"做了什么，并注明"未特别说明的逻辑均复用 `源技能`"
- **覆盖需有因果**：每项覆盖必须说明覆盖原因（如"因本技能无确认步骤兜底"），让读者理解为什么不能直接复用源技能的行为

**覆盖规则的编写格式：**

```markdown
### 步骤 N. 执行源技能流程（覆盖模式）

复用 `源技能名称` 的完整流程，并应用以下覆盖规则：

**XX 覆盖**：<覆盖后的行为>。<覆盖原因>。

**YY 覆盖**：<覆盖后的行为>。<覆盖原因>。
```

**安全边界的覆盖写法：**

```markdown
## 安全边界

复用 `源技能名称` 的安全边界，并叠加以下覆盖：

- <覆盖项>（覆盖源技能的 <原策略>，<覆盖原因>）
```

**反例——将派生技能写成独立完整描述：**

```markdown
### 步骤 2. 调用源技能流程

优先复用 `源技能` 的完整流程，包括：

1. 分析当前状态
2. 理解改动意图
3. 生成规范提交信息
4. 执行暂存与提交

**安全边界：**

- 禁止执行 push、pull、merge ← 源技能已定义，无需重复
- 禁止使用 --no-verify ← 源技能已定义，无需重复
```

**正例——薄覆盖层写法：**

```markdown
### 步骤 2. 执行源技能流程（覆盖模式）

复用 `源技能` 的完整流程，并应用以下覆盖规则：

**确认步骤覆盖**：跳过交互确认，直接执行。但因无确认步骤兜底，敏感文件处理从仅警告升级为停止提交。

## 安全边界

复用 `源技能` 的安全边界，并叠加以下覆盖：

- 发现凭证、私钥时停止提交（覆盖源技能的仅警告策略，因本技能无确认步骤兜底）
```

## 目录结构规范

```text
skill-name/
├── SKILL.md          # 必需，技能主文件
├── scripts/          # 可选，脚本目录（可执行技能）
│   ├── Node.js 方式
│   │   ├── main.ts       # 主执行脚本
│   │   └── package.json  # 依赖配置
│   └── Python 方式
│       ├── read_pdf.py       # 主执行脚本
│       ├── pyproject.toml    # 依赖配置（推荐）
│       └── requirements.txt  # 依赖配置（兼容旧方式）
├── examples/         # 可选，示例目录
│   ├── input.md      # 输入示例
│   └── output.md     # 输出示例
├── templates/        # 可选，模板目录
│   └── example.md    # 模板文件
├── resources/        # 可选，资源目录
│   └── reference.md  # 参考文档
└── prompts/          # 可选，提示词派生产物目录
    └── skill-prompts.md  # 由 SKILL.md 派生出的系统提示词
```

### 目录说明

- `SKILL.md`：**必需**，技能主文件，定义技能名称、描述、使用场景、指令
- `scripts/`：**可选**，可执行技能需要脚本文件时使用。脚本文件命名遵循目标语言的常见约定：Node.js/TypeScript 文件优先使用 kebab-case（如 `wechat-api.ts`，入口文件可使用 `main.ts` 或 `main.js`），Python 文件优先使用 snake_case（如 `read_pdf.py`）。依赖配置放在 `scripts/package.json`（Node.js）；Python 依赖配置优先使用 `scripts/pyproject.toml`，也兼容 `scripts/requirements.txt`
- `examples/`：**可选**，技能使用方式不直观时提供示例说明
- `templates/`：**可选**，需要生成特定格式文件或模板实际内容超过 20 行时使用（计数规则：只统计实际内容行，不含空行、代码块围栏标记行、YAML frontmatter 行）
- `resources/`：**可选**，需要参考文档或素材文件时使用
- `prompts/`：**可选**，存放由 SKILL.md 派生出的系统提示词文件，默认文件为 `prompts/skill-prompts.md`；该目录是派生产物目录，不作为技能主定义来源，优先由 `yy-skill-to-prompt` 生成

## 交互设计原则

### 减少不必要的交互轮次

技能执行时应尽量减少与用户的交互次数，提高执行效率。

**核心原则：默认采用最常见策略，仅在用户明确要求时才提供选项。**

### 常见交互优化模式

#### 模式 1：默认策略优先

**错误做法**：每次都询问用户选择策略

```markdown
### 步骤 2. 处理现有文件

询问用户更新策略：

1. 覆盖：完全重新生成
2. 补充：保留现有内容，补充缺失部分
3. 优化：优化现有内容的结构和表达
```

**正确做法**：默认采用最常见策略，仅在明确要求时才覆盖

```markdown
### 步骤 2. 处理现有文件

- 读取现有文件内容
- 分析现有结构和内容
- 默认采用"补充+优化"策略：保留现有内容，补充缺失部分，优化表达和结构
- 若用户明确要求"完全重写"，则覆盖生成
- 若目标技能明确但修改范围未细化，先展示计划，再按当前确认分支直接执行或等待确认
```

#### 模式 2：精简引导问题

**错误做法**：列出过多引导问题

```markdown
使用以下引导性问题帮助用户明确需求：

1. 项目是什么？
2. 为什么开发？
3. 有什么特点？
4. 学到了什么？
5. 还有什么补充？
```

**正确做法**：只保留核心问题

```markdown
使用以下引导性问题帮助用户明确需求：

1. 项目是什么？- 一句话描述核心功能
2. 为什么开发？- 开发动机、解决什么问题
3. 有什么特点？- 与同类项目的差异点
```

#### 模式 3：快速提交模式

对于需要用户确认的操作，支持快速模式：

```markdown
如果用户在请求中使用了以下关键词，则跳过确认步骤：

- 直接提交、立即提交、马上提交
- 无需确认、不用确认、跳过确认

仅当目标、范围和默认策略已足够明确时，才可命中快速模式；若信息仍不完整，仍需先补齐或确认。
```

### 交互设计检查清单

- [ ] 是否有必须询问用户才能继续的步骤？
- [ ] 默认策略是否覆盖 80% 以上的使用场景？
- [ ] 引导问题是否都是核心必要问题？
- [ ] 是否支持快速模式跳过确认？

## 技能触发方式

- **自动触发**：当用户要执行的操作与技能的 description 内容相匹配时自动触发，如：`请审查这个 PR 的风险`。
- **显式调用**：当用户主动提及技能名称时触发，如：`使用 pr-risk-check 技能来审查当前分支相对于 main 分支的差异。`。

## 常见问题与解决方案

### 问题 1：技能写成知识文档

**错误做法**：

```markdown
## 什么是技能

技能是一种可复用的任务说明书...

## 技能的优点

1. 可以复用
2. 可以共享
```

**正确做法**：

```markdown
## 指令

### 步骤 1. 理解用户需求

### 步骤 2. 确定技能目标

### 步骤 3. 编写 SKILL.md

### 步骤 4. 验证技能格式
```

### 问题 2：缺少负例

**错误做法**：

```markdown
## 使用场景

- 用户提到代码审查

（没有列出不应触发的场景）
```

**正确做法**：

```markdown
## 使用场景

- 用户提到代码审查

不应触发：

- 用户要求直接修改代码
- 用户只是询问代码问题
```

### 问题 3：指令不清晰

**错误做法**：

```markdown
## 指令

根据情况处理
```

**正确做法**：

```markdown
## 指令

### 步骤 1. 读取项目配置文件

### 步骤 2. 分析项目结构

### 步骤 3. 输出结果：文件路径、变更摘要、验证结果
```

### 问题 4：决策点模糊

**错误做法**：

```markdown
### 步骤 3. 执行检查

执行命令并根据结果处理。
```

**正确做法**：

```markdown
### 步骤 3. 执行检查

执行命令并捕获 exit code：

- **exit code 为 0**：检测通过，显示成功消息
- **exit code 非 0**：读取错误日志，分析并修复问题
```

## 验收清单

### 通用检查项

1. `## 描述` 章节准确反映技能用途
2. description 遵循结构化公式，包含排除条件，不会误触发
3. 使用场景明确（触发条件和不应触发场景）
4. 指令步骤完整可执行，最后一步描述输出格式
5. YAML 格式正确
6. **决策点显式化**：步骤中隐含的分支选择已转化为明确规则
7. **文件间一致性**：SKILL.md 与辅助文件对同一事项描述一致；如存在 prompts/skill-prompts.md，其提示词内容应覆盖 SKILL.md 的核心角色、流程、约束和输出规则
8. **安全边界**：涉及敏感操作的技能已明确禁止行为
9. **受众意识**：SKILL.md 不包含对执行技能无意义的内部实现细节（如底层模块/组件文件清单、源代码文件逐项列举等）

### 创建技能后检查项

1. 文件命名符合规范（kebab-case）
2. 使用中文描述
3. 代码示例包含语言标签
4. 如果有参考文档需求，已添加 `resources/` 目录
5. 如有脚本文件，Node.js/TypeScript 文件优先使用 kebab-case，入口文件可使用 `main.ts` 或 `main.js`；Python 文件优先使用 snake_case，依赖配置放在 `scripts/package.json`（Node.js）；Python 依赖配置优先使用 `scripts/pyproject.toml`，也兼容 `scripts/requirements.txt`
6. 如有 evals 测试用例，格式正确
7. SKILL.md 包含执行步骤，不是纯知识文档
8. 未在 SKILL.md 中内嵌过长模板代码（实际内容超过 20 行应移至 templates/，不含空行和代码块标记行）
9. 如需生成提示词派生产物，默认不手写 `prompts/skill-prompts.md`，优先由 `yy-skill-to-prompt` 生成
10. 当前环境已安装 `yy-skill-to-prompt` 时，默认生成或更新 `prompts/skill-prompts.md`；未安装时，允许跳过但需说明原因
11. 未安装 `yy-skill-to-prompt` 且使用本地最小回退流程时，必须同时满足“用户明确要求生成提示词文件”和“用户已确认使用回退流程”
12. 未在 SKILL.md 中罗列对执行技能无意义的底层实现细节（如模块/组件文件清单、源代码文件逐项列举等）

### 更新技能后检查项

1. description 只保留触发判断所需信息，没有混入执行细节
2. 默认只修改 `SKILL.md` 和必要的派生产物；如本次变更导致辅助文件失配，则同步更新相关辅助文件
3. 步骤编号、章节名称、术语是否与辅助文件一致
4. 如有 prompts/skill-prompts.md，检查其内容是否需要根据 SKILL.md 的更新同步重新生成
5. 未安装 `yy-skill-to-prompt` 且使用本地最小回退流程时，必须同时满足“用户明确要求生成提示词文件”和“用户已确认使用回退流程”

## 质量要求

- **长度控制**：SKILL.md 应控制在 500 行以内，超出内容移至 resources
- **语言风格**：使用祈使语气（"做 X"），使用中文描述
- **代码示例**：包含语言标签

## 路径格式规范

- 使用正斜杠作为路径分隔符，路径包含空格时使用引号包裹，以确保跨平台兼容性和正确解析
