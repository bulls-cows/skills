# 工作流程

本文档详细描述 yy-lint 技能的执行流程和实现细节。

## 阶段一：确定要执行的命令

**优先级顺序（从高到低）：**

1. 用户明确指定的命令
2. `package.json` 中的 `lint:fix` 脚本
3. `package.json` 中的 `lint` 脚本

**执行逻辑：**

1. 检查用户是否提供了自定义命令参数
   - 如果有，直接使用该命令，跳过步骤 2-3，进入阶段二
2. 检查项目根目录下是否存在 `package.json` 文件
   - 如果存在，读取 `package.json` 中的 `scripts` 字段
3. 检查是否定义了 `lint:fix` 或 `lint` 命令（优先 `lint:fix`）

**决策分支：**

| 条件                              | 行为                   |
| --------------------------------- | ---------------------- |
| 用户指定了自定义命令              | 使用该命令，进入阶段二 |
| package.json 不存在或无 lint 脚本 | 显示提示，结束执行     |
| 存在 lint 相关脚本                | 记录命令，进入阶段二   |

## 阶段二：验证 Node 版本

1. 检查项目根目录下是否存在 `.nvmrc` 文件
2. 如果存在，读取文件内容获取要求的 Node.js 版本
3. 使用 `node --version` 获取当前 Node.js 版本
4. 比较版本是否满足要求

**决策分支：**

| 条件                    | 行为               |
| ----------------------- | ------------------ |
| .nvmrc 不存在或无法读取 | 继续执行阶段三     |
| Node 版本满足要求       | 继续执行阶段三     |
| Node 版本不满足要求     | 显示警告，结束执行 |

## 阶段三：执行命令检查

执行阶段一确定的命令（可能是用户指定的自定义命令或自动检测到的 lint 命令）。

**关键行为：**

1. 执行 lint 命令并捕获 exit code
   - **重要**：在捕获到 exit code 值之前，绝对不要读取 lint 命令的输出内容
   - 必须先获取 exit code，再根据结果决定后续操作
   - 这是为了避免在 lint 通过时浪费 token 读取无用的成功日志

2. **exit code 为 0**：
   - 检测通过，显示成功消息
   - **不要读取命令输出日志**，直接结束执行

3. **exit code 非 0**：
   - 读取错误日志
   - 进入阶段四定位根因，**不得在未定位根因前直接修改代码**

## 阶段四：定位报错根因

**核心规则：先定位根因，再尝试修复；无法定位根因时不盲目修复。**

1. **归类报错**：按规则类型（如未使用变量、类型错误、格式问题）和涉及文件对报错分组，识别级联报错——同一根因引发的多条报错只算一个问题
2. **定位触发位置**：打开报错涉及的源文件及相关配置文件，确认报错的实际触发位置，不依赖日志字面信息猜测
3. **判断根因类型**：

| 根因类型        | 典型特征                                  |
| --------------- | ----------------------------------------- |
| 代码问题        | 报错指向具体业务代码，修复点明确          |
| 配置问题        | 报错指向 ESLint 配置、tsconfig 等配置文件 |
| 依赖/工具链问题 | 报错与依赖版本、工具版本或缺失包有关      |

**决策分支**：

| 条件                           | 行为                                         |
| ------------------------------ | -------------------------------------------- |
| 根因明确、修复方式确定         | 进入阶段五                                   |
| 报错信息不足以判断根因         | 不修改文件，输出报错清单和初步分析，结束执行 |
| 级联报错找不到源头             | 不修改文件，输出报错清单和初步分析，结束执行 |
| 疑似配置或工具链异常且无法确认 | 不修改文件，输出报错清单和初步分析，结束执行 |

无法定位根因而结束时，输出内容应包含：报错清单（按文件分组）、已排查的方向、建议人工介入的检查点。

## 阶段五：评估修复规模与确认

根据已定位的根因，评估修复方案预计涉及的改动范围。

**大规模改动判定**（满足任一即视为大规模）：

- 预计修改文件 ≥ 10 个
- 需要修改 lint 或 TypeScript 全局配置文件（如 ESLint 配置、tsconfig）
- 根因指向依赖或工具链（需要升级、更换依赖或调整工具版本）

**决策分支**：

| 条件               | 行为                                   |
| ------------------ | -------------------------------------- |
| 小规模改动         | 直接进入阶段六修复                     |
| 大规模改动         | 先输出修复方案，等待用户明确答复       |
| 用户确认采纳方案   | 进入阶段六修复                         |
| 用户拒绝或要求调整 | 按用户意见处理，未确认前不修改任何文件 |

大规模改动的修复方案必须包含：

- 报错分类及各类根因说明
- 涉及文件清单（或文件范围与预计数量）
- 每类报错的修复方式
- 配置或依赖变更说明（如有）

## 阶段六：修复报错并验证

**核心规则：只修复已定位根因的报错，不修复警告。**

### 报错修复要求

修复 lint 报错时必须**正面解决问题**，不得回避：

| 行为                            | 是否允许 | 原因                   |
| ------------------------------- | -------- | ---------------------- |
| 理解报错含义，针对根本问题修复  | ✅ 允许  | 正面解决问题           |
| 添加 `any` 类型声明绕过类型检查 | ❌ 禁止  | 掩盖潜在类型错误       |
| 删除未完成的功能代码消除报错    | ❌ 禁止  | 破坏用户工作进度       |
| 未定位根因时试探性修改代码      | ❌ 禁止  | 盲目修复可能引入新问题 |

修复完成后重新执行 lint 命令验证：仍有报错时回到阶段四重新定位，不得对新报错跳过定位直接修复。

### 警告不修复的原因

- 警告通常为建议性提示，不影响代码功能
- 自动修复警告可能引入不必要的修改
- 保留警告供开发人员人工评估是否需要调整

## 并行任务约束

**规则：有并行任务时禁止执行 lint。**

**原因**：lint 命令可能会自动修改本地代码（格式化等），若某个并行任务正在写入文件，可能导致文件内容异常或冲突。

**执行时机**：等所有并行任务完成后，再统一执行一次 lint。

## Token 优化策略

执行 lint 命令后的处理逻辑：

```javascript
if (exitCode === 0) {
  // 检测通过，无需读取日志
  console.log('✓ 代码质量检查通过！')
  return
} else {
  // 检测失败，需要读取日志进行分析
  console.log('✗ 检测失败，读取错误日志...')
  const output = readCommandOutput()
  // ... 处理错误
}
```

**原因**：exit code 为 0 表示检测通过，读取大量成功日志纯属浪费 token。

## 安全边界

**禁止主动执行的命令**：

- 除 lint 相关命令（`npm run lint:fix` 或 `npm run lint`）外的 `package.json` 中定义的其他命令
- 编译命令、构建命令、部署命令
- 任何自动执行的测试命令
- 除 `node --version` 外的其他 `npx` 命令
