## 1. 开头范例

**直入问题型（推荐）**：

> 给 Vue 组件写 name 是一件不起眼但绕不开的事。Vue Devtools 的组件树显示依赖它，keep-alive 的 include/exclude 匹配依赖它，递归组件的自身引用也依赖它。但组件名几乎总是等于文件名，手动编写属于重复劳动。

特点：第一句点明问题，第二句展开说明影响面，第三句点出核心矛盾。

**场景切入型（推荐）**：

> 线上排查 bug 时最常遇到的一个问题：当前环境跑的是哪个版本的代码？本地无法复现的 bug，可能是版本没部署到位，也可能是缓存没更新。如果能一眼看出当前环境的编译时间和代码版本，排查效率会高很多。

特点：先描述一个具体场景，让读者带入，再引出方案。

**结论先行型（适用长文）**：

> 对一个有 400 多个页面的 Webpack 3 项目，编译一次需要 75 分钟。优化后的编译时间降到 15 分钟以内。核心思路不是提高 webpack 编译速度，而是按目标环境只按需编译需要的页面。

特点：先把结论和关键数据抛出来，让读者知道这篇文章值得看。

**不推荐的开头**：

- 故事化开头："我之前有个项目，遇到一个特别头疼的问题..."
- 情感化开头："做前端最怕的一种情况是，测试跑过来说线上有个 bug..."
- 设问式开头："你有没有想过，给组件写 name 这件事，其实完全可以交给机器干？"

## 2. 分节标题写法

**推荐的结构化标题**：

```markdown
## 一、背景

## 二、核心逻辑

### 2.1、全局变量注入

### 2.2、HTML 占位符替换

### 2.3、data-build 属性标记

## 三、工具函数

## 四、通过 Vite 插件落地
```

**推荐的分节方式**：

- 使用 "一、二、三" 作为一级分节
- 使用 "2.1、2.2" 或 "①、②" 作为二级分节
- 标题是名词性短语，不写成完整句子
- 标题能反映该节的核心内容

**不推荐的标题写法**：

- 模糊标题："一些思考"、"相关讨论"
- 叙事标题："开始之前"、"让我先说说"
- 无编号的长篇连续段落

## 3. 代码与说明的搭配

**推荐的写法**：先给代码，再做要点说明。

> ```js
> const filePathRegex = /src\/pinlanUI\/components\/.+\.vue$/
> const defineComponentNameRegex = /<script lang="ts">/
>
> export default function plUiPlugin() {
>   return {
>     name: 'pl-ui-plugin',
>     enforce: 'pre',
>     transform(src, id) {
>       if (filePathRegex.test(id)) {
>         const componentName = id.match(/[a-zA-Z]+(?=\.vue)/)?.[0] || ''
>         return {
>           code: defineComponentNameRegex.test(src)
>             ? src
>             : `${src}${getTemplateDefineComponentName(componentName)}`,
>           map: null,
>         }
>       }
>     },
>   }
> }
> ```
>
> 核心逻辑分三步：
>
> **第一步，限定范围**。通过 `filePathRegex` 只处理目标目录下的 Vue 文件。
> **第二步，提取组件名**。`id.match(/[a-zA-Z]+(?=\.vue)/)` 从路径中匹配文件名。
> **第三步，判断并注入**。检查源码是否存在 `<script lang="ts">`，不存在则追加。

特点：代码完整可运行，要点说明紧跟在代码之后，一一对应。

**不推荐的写法**：

- 先说一大段原理再给代码，读者需要来回对照
- 只贴代码片段不给上下文
- 代码和说明分离（代码在前面，说明在后面很远的地方）

## 4. 技术要点说明风格

**推荐的短句引出风格**：

> 采用三层兜底策略：
>
> 1. **环境变量 `BUILD_VERSION`**：为 CI/CD 准备，Docker 等构建环境不一定有 git，通过流水线注入最可靠。
> 2. **`git symbolic-ref --short -q HEAD`**：获取当前分支名，适用于本地开发。
> 3. **`git describe --tags`**：detached HEAD 状态下的 fallback，获取最近的 tag 名。

特点：用粗体标识关键术语，紧跟一句话说明"是什么"和"为什么"。

**推荐的细节说明风格**：

> `<script setup>` 可以和普通 `<script>` 同时存在。普通 `<script>` 专门用于处理 setup 里做不了的事，比如定义 `inheritAttrs`，也包括 `name`。Vue 3 运行时会自动将两个 script 块合并成一个组件定义。

特点：先给结论，再解释原因，最后补充运行时行为。

**不推荐的说明风格**：

- 用比喻替代技术说明："这跟给每本书抄一遍封面标题似的"
- 过度解释："很多人不知道，Vue 3 有一个小知识..."
- 第一人称评价："我觉得这个方案特别好用"

## 5. 对比与取舍说明

**推荐的对比风格**：

> 这里有两个方案：一是通过 webpack loader 在编译时替换，二是通过运行时注入。编译时替换的优势在于不增加运行时开销，缺点是修改后需要重新构建。运行时注入灵活但会有额外的性能损耗。对于组件 name 这种编译期就确定的信息，编译时处理更合适。

特点：列出对比维度，给出选择理由，不做主观评价。

**推荐的取舍说明**：

> 这种前端生成 uid 的方案，如果带入一个单客户端里单调递增的全局 ID，后期可以扩展实现复现用户端接口请求顺序的功能。但缺点是增加了请求包体的大小。这里需要根据实际场景权衡。

特点：同时列出优点和缺点，不回避 trade-off。

## 6. 细节提示与注意事项

**推荐的注意事项风格**：

> `transformIndexHtml` 这个钩子是 Vite 特有的，Rollup 里没有。Rollup 主要处理 JavaScript 模块，HTML 处理是 Vite 在开发服务器和构建时额外提供的能力。

特点：指出容易被忽略的边界情况，用短句直接说明。

> 注意，这个 loader 要尽早被使用到。在 webpack 配置中，位置越靠后的 loader 会越先被用到。

特点：给出实际操作中容易踩的坑，附带原因。

**不推荐的提示风格**：

- "这里有个细节值得注意"（只说值得注意，不说为什么值得注意）
- "踩坑警告"（过度戏剧化）
- 用感叹号表达紧迫感

## 7. 收尾范例

**总结收束型（推荐）**：

> 把插件注册到 vite.config.ts 之后，所有目标目录下的组件都会自动拥有正确的组件名。核心逻辑只有三步，三十行不到——关键在于 `enforce: 'pre'` + `transform` 钩子这个组合，在编译入口处完成了组件名的自动注入。

特点：回顾方案的核心价值，最后落回到关键技术的总结上。

**方案对比型（推荐）**：

> 这个方案对比手动编写 name，减少了重复劳动和漏写风险。对比通过 lint 规则强制要求编写 name，又不需要每个组件都维护一段重复代码。缺点是需要在构建工具中额外配置一个插件，但对于团队项目来说，一次配置长期受益。

特点：与替代方案做简要对比，给出客观评价。

**不推荐的收尾**：

- 情感化总结："这种账，值得算"、"这种钱，值得花"
- 空洞升华："希望本文对你有所帮助"
- 自夸式结尾："这个方案真的特别好用"
