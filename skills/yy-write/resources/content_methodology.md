## 1. 选题方法论

### 选题交集模型

一个好的技术选题 = 真实的问题场景 + 可落地的技术方案 + 足够的技术细节

- **真实的问题场景**：读者能带入，知道"这说的是我遇到的问题"
- **可落地的技术方案**：有具体实现，不是纯理论讨论
- **足够的技术细节**：有代码、配置、数据，读者能照着做

### 选题来源

- **项目经验**：实际开发中踩过的坑、做过的优化，这是最可靠的选题来源
- **团队共性问题**：多个同事遇到过的相同问题，说明有代表性
- **技术社区讨论**：GitHub Issues、Stack Overflow、技术论坛中高频出现的问题
- **技术方案复盘**：架构决策、技术选型的取舍过程

### 选题评估

动笔前用 RSD 评估选题强度：

| 维度   | 强                             | 中                   | 弱               |
| ------ | ------------------------------ | -------------------- | ---------------- |
| R 真实 | 多数开发者都遇到过             | 特定场景下会遇到     | 罕见或假设场景   |
| S 方案 | 有完整可运行的代码/配置        | 有核心思路和关键代码 | 仅有方向性建议   |
| D 细节 | 有完整代码、对比数据、注意事项 | 有核心代码和关键说明 | 缺少具体实现细节 |

**决策规则**：

- S 级选题：三项全强
- A 级选题：R 强 + S 强（可缺 D）
- B 级选题：R 强 + D 强（可缺 S，但需补充方案）
- 不推荐：S 弱且 D 弱，或 R 弱

## 2. RSD 质检法

动笔前每个选题必须通过 RSD 质检：

### R (Real) 真实度检查

- 这个问题是自己实际遇到的，还是推测的？
- 目标读者群体中，有多少比例会遇到这个问题？
- 问题描述是否包含了真实的上下文和约束条件？

**判定标准**：

- 强：自己亲自踩过坑，能描述完整上下文
- 中：同事或团队遇到过的共性问题
- 弱：阅读资料时看到的，未实际验证

### S (Solution) 方案完整度检查

- 方案是否有完整的代码或配置实现？
- 方案是否经过实际验证（编译通过、运行正常）？
- 方案是否有明确的落地步骤？

**判定标准**：

- 强：有完整代码，已在实际项目中验证
- 中：有核心代码，但缺少完整上下文
- 弱：仅有思路，缺少具体实现

### D (Detail) 细节充分度检查

- 是否有关键代码片段，且代码有必要的说明？
- 是否说明了方案的边界条件和注意事项？
- 如果有多种方案，是否做了对比和取舍分析？

**判定标准**：

- 强：代码完整、有对比、有注意事项、有踩坑记录
- 中：有核心代码和关键说明
- 弱：缺少具体实现细节或对比分析

## 3. 技术文章结构模板

### 方案说明型（最常用）

```markdown
## 一、背景

- 说明问题是什么
- 说明为什么需要解决这个问题
- 说明现有做法有什么不足

## 二、核心方案

- 整体思路
- 关键代码（完整可运行）
- 要点说明（代码之后，逐条对应）

## 三、关键细节

- 容易被忽略的边界情况
- 技术原理说明
- 注意事项

## 四、落地方式

- 如何集成到现有项目
- 配置方式
- 验证方法
```

适用场景：技术方案介绍、功能实现、工具封装。

### 问题排查型

```markdown
## 一、现象

- 问题表现
- 影响范围

## 二、排查过程

- 排查思路
- 每一步的发现和排除

## 三、根因分析

- 根因是什么
- 为什么会导致现象

## 四、解决方案

- 修复方式
- 验证结果
- 预防措施
```

适用场景：bug 修复记录、性能问题排查。

### 最佳实践型

```markdown
## 一、场景与痛点

- 什么场景下需要
- 不这样做会有什么问题

## 二、推荐做法

- 核心实现
- 关键代码

## 三、对比分析

- 与替代方案对比
- 各自优缺点
- 选型理由

## 四、注意事项

- 容易踩的坑
- 边界情况处理
```

适用场景：技术选型、规范制定、架构设计。

### 原理分析型

```markdown
## 一、问题引出

- 一个具体的疑问或现象

## 二、逐步深入

- 从表象到源码/原理
- 关键环节的代码或机制说明

## 三、总结

- 核心结论
- 实际应用建议
```

适用场景：源码解读、机制分析。

## 4. 内容质量标准

### 信息密度

- **每段都有信息量**：没有凑字数的铺垫句、过渡句
- **代码占合理比重**：技术文章的核心是代码和说明，不是故事和感受
- **说明要解释"为什么"**：不只是展示代码，要说明为什么这样写

### 可操作性

- **代码可运行**：文章中的代码片段应该是完整的，至少核心逻辑完整
- **步骤可跟随**：读者能按文章顺序操作，不需要自己补中间步骤
- **配置可复制**：配置项、命令应该是可以直接复制使用的

### 客观性

- **方案要说明取舍**：没有银弹，好的技术文章会说明方案的局限性
- **对比要公平**：对比多个方案时，使用相同的对比维度
- **数据要真实**：性能数据、测试结果必须是真实的，不能编造

### 结构完整性

- **有头有尾**：有背景说明，有方案总结
- **逻辑递进**：分节之间是递进关系，不是并列罗列
- **闭环收尾**：结尾回应开头的问题，说明方案解决了什么问题
