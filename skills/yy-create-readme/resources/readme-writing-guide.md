# README 编写参考

## 常见问题

### 1. 描述太泛泛

**问题**：描述像"一个 XX 管理系统"，没有说明价值。

**改进**：说明解决的具体问题，如"帮助团队追踪任务进度，支持看板视图和甘特图"。

### 2. 缺少技术栈

**问题**：没有列出技术栈，读者需要翻 package.json。

**改进**：单独列出技术栈章节，分类展示前端、后端、数据库等。

### 3. 安装命令不完整

**问题**：只写 `npm install`，缺少克隆、进入目录等步骤。

**改进**：提供从零开始的完整命令序列。

### 4. 没有界面展示

**问题**：有 UI 的项目缺少截图。

**改进**：添加截图或 GIF，让读者快速了解项目外观。

### 5. 特性列表空洞

**问题**：特性写"功能强大"、"易于使用"等空话。

**改进**：写具体功能，如"支持 Markdown 语法"、"提供暗色主题"。

### 6. 缺少环境变量和资源占位说明

**问题**：项目依赖 `.env` 文件或外部资源目录，但 README 未说明如何配置。

**改进**：

- 提供 `.env.example` 文件并说明复制和修改方式
- 用表格列出关键环境变量名、含义和默认值
- 明确资源占位目录（如 `assets/`、`screenshots/`），说明哪些需要替换为真实资源
- 不将真实 `.env` 文件内容直接写入 README，避免泄露密钥

## Emoji 使用指南

### 推荐使用的 emoji

**特性列表：**

- ⭐ 重要特性
- 🚀 核心功能、高性能
- 💡 创新点、亮点
- 🎯 目标、精准定位
- ⚡ 快速、高效
- 🔒 安全相关
- 📊 数据、统计相关
- 🎨 UI/UX 相关

**技术栈分类：**

- 🖥️ 前端技术
- ⚙️ 后端技术
- 🗄️ 数据库
- 🧰 开发工具
- ☁️ 云服务
- 📱 移动端

**其他场景：**

- 📦 环境要求、依赖
- 📄 协议、文档
- 🚧 开发中、待完善
- ✅ 已完成、支持

### 使用原则

1. **适度使用**：每个列表项最多使用一个 emoji，避免过度使用
2. **保持一致**：同类内容使用相同的 emoji
3. **语义匹配**：选择与内容含义相符的 emoji
4. **中英文混排**：中文描述配合 emoji，专有名词保留英文

## 注意事项

- 使用正斜杠作为路径分隔符，路径包含空格时使用引号包裹，以确保跨平台兼容性和正确解析
- 不要假设项目使用未发现的框架或工具
- 如果无法确定某些信息，主动询问用户
- 保持 README 的简洁性，详细文档可放在 `docs/` 目录
- 尊重用户现有的 README 结构偏好
- 对于已部署的项目，建议提供在线访问链接
- 合理使用 emoji 表情增强文档视觉效果，但不要过度使用
