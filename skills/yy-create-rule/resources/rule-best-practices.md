# 规则内容编写最佳实践

本文档提供规则文档编写的最佳实践参考，帮助创建高质量、易维护的规则文档。

## 规则文档本质

规则文档是"给 AI 的项目知识库"，用于记录项目特定的规范、最佳实践和经验教训。关键特点：

1. **面向 AI 读者**：写的是给下一次对话中的 AI 看的，要清晰、无歧义、可操作
2. **具体而非抽象**：给出代码示例、文件路径、具体场景，而非泛泛而谈
3. **避免文档碎片化**：不要将同一条内容写进多个文件
4. **通用性而非特定数据**：规则必须是可复用的指导原则，不能记录特定项目的具体数据（如具体行数、具体版本号、具体项目名等）；这些数据对其他项目没有指导意义，且会随时间失效

## 内容结构模板

规则文档应使用标准的 Markdown 层级结构：

```markdown
### [章节标题]

**[子标题或要点]**

[详细描述]

**[示例/代码]**（如果适用）

\`\`\`[语言]
[代码示例]
\`\`\`

**[注意事项]**（如果适用）

- 注意事项1
- 注意事项2
```

## 语言规范

- 文档主体使用中文
- 专有名词（`Vue`、`TypeScript`、`React`）、代码片段、已广泛使用的技术缩写（`API`、`SDK`、`OSS`）保留英文
- 正文叙述不夹杂不必要的英文，如"这个 component 需要 emit 一个 event"应改为"该组件需要通过事件通知父级"

## 编写原则

### 规则文档的编写原则

1. 使用标准的 Markdown 层级结构
2. 章节标题要具有描述性
3. 使用列表和代码块增强可读性
4. 将相似的规范/实践归类到同一章节
5. 提供具体的代码示例
6. 说明"为什么"而不仅仅是"怎么做"
7. 包含反例说明（如果适用）
8. 根据规则适用范围选择合适的触发模式（`always_on` / `glob` / `model_decision` / `manual`），详见 `content-template.md`

### 保持一致性

- 遵循现有文档的格式风格
- 使用一致的术语和命名
- 保持章节编号/层级的一致性

### 避免重复

- 更新前先检查是否已存在类似内容
- 如果已存在，考虑补充或改进现有内容，而不是添加重复内容

## AGENTS.md 引用格式

在 AGENTS.md 中添加对规则文档的引用：

```markdown
## 需要遵守的规则

- [规则名称 @rules/vue-component-norms/RULE.md](./rules/vue-component-norms/RULE.md)
- [规则名称 @rules/api-best-practices/RULE.md](./rules/api-best-practices/RULE.md)
```

引用格式：`- [规则名称 @rules/[目录名]/RULE.md](./rules/[目录名]/RULE.md)`

规则名称要清晰，让 AI 能够快速了解该规则文档的作用。

## 注意事项

- 使用正斜杠作为路径分隔符，路径包含空格时使用引号包裹
- 在更新文档前，务必先读取文档内容，了解现有结构
- 不要删除或修改现有内容，除非用户明确要求
- 如果不确定应该放在哪个章节，询问用户的意见
- 保持专业和简洁的技术写作风格
- 使用中文编写内容（除非项目文档是英文）
- 规则目录下的文件内容深度 > AGENTS.md 的引用说明深度
- 如果用户提供的内容已经在文档中存在，告知用户并说明在哪里，不重复写入
- 对于非常临时或版本相关的信息（如"某个依赖的临时 bug"），写入时标注"临时"或版本号
- 确保 AGENTS.md 文件存在，如果不存在提示用户使用 `/yy-create-agents` 命令创建

## 质量要求

- **长度控制**：单个文件不超过 500 行，超过 300 行时考虑是否需要拆分或精简；优先精简语言减少行数，其次才拆文件
- **语言风格**：使用祈使语气（"做 X"），使用中文描述
- **代码示例**：包含语言标签
