# 提交原子性判断标准

## 核心标准

一次提交是否构成一个原子逻辑单元——所有改动围绕同一意图、共享同一回滚边界，单独取出任一部分都不影响其余部分的可工作性。

## 参考信号——倾向应拆分为多次

- 变更涉及多个不相关的功能或模块（如同时修改了认证模块和支付模块）
- 变更中既包含功能开发又包含 bug 修复，且二者无直接因果关联
- 变更中既包含业务代码又包含配置文件/构建脚本的调整，且二者无直接依赖
- diff 内容中出现多个独立的逻辑单元，每个单元都可以独立工作

## 参考信号——倾向无需拆分

- 所有改动围绕同一个功能或同一个问题
- 改动之间存在明确的因果或依赖关系
- 改动总量较小，拆分后单个提交缺乏独立意义
