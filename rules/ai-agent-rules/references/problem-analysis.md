# 问题分析与定位

## 触发时机

- 定位问题前
- 提出方案前
- 分析需求时

## 约束与验收识别

### 行动前先提取边界条件

**规则**：在开始分析或执行前，先提取以下边界：

- 语言约束（中文/英文/特定术语）
- 范围约束（允许修改的目录和文件）
- 兼容性约束（不能破坏的现有行为）
- 授权约束（需要用户确认的操作）
- 验证约束（如何验证结果正确）
- 交付约束（输出格式和内容要求）

**要求**：边界未明确时，先确认再推进，不在前提未明时直接执行。

### 同步识别验收标准

**规则**：识别任务目标时，同步明确：

- 成功标准：什么状态算完成
- 失败条件：什么情况需要回退或放弃
- 回归要求：哪些现有行为不能被破坏

将验收口径转化为全过程约束，而非事后检查。

## 证据收集

### 优先收集可验证事实

**规则**：定位问题时，先收集可验证的事实，再给出结论。

**要求**：

- 区分表象（报错信息）、根因（为什么出错）和影响范围（哪些功能受影响）
- 不用直觉替代定位，每个结论都要有证据支撑
- 证据来源：错误日志、文件内容、git 历史、工具输出

### 先用最小必要信息判断

**规则**：先用最小必要样本完成判断，只有在证据不足时才扩展上下文。

**要求**：

- 读取相关文件时，先读关键部分（错误位置、接口定义、配置项）
- 信息不足时再扩大范围，避免无差别全量展开
- 明确区分"已确认的事实"和"待验证的假设"

### 信息不足时显式降级

**规则**：当信息不足以支撑结论时，明确标记状态，不用猜测补齐空白。

**要求**：

- 标记为"需确认"：有线索但未验证
- 标记为"待验证"：有假设但缺证据
- 标记为"跳过"：与当前任务无关，不影响主流程

## 结构分析

### 快速识别分层和边界

**规则**：进入代码库时，快速识别以下结构信息：

- 模块分层（展示层、调度层、规则层、数据层、工具层）
- 职责边界（每个模块/文件的核心职责）
- 命名层级（命名规范、命名与实际职责的对应关系）
- 异常分布（重复结构、职责错位、命名偏离）

### 识别依赖关系

**规则**：修改前识别以下依赖关系：

- 步骤依赖：操作 A 必须在操作 B 之前完成
- 模块依赖：文件 A 引用了文件 B 的导出
- 数据依赖：字段 A 的值依赖字段 B 的计算结果
- 文档依赖：说明文档引用了特定的代码结构或接口

避免局部修改破坏整体顺序。

### 从入口到结果做闭环检查

**规则**：分析问题时，沿完整链路检查：

1. 入口：用户操作或触发条件
2. 处理：中间逻辑和状态转换
3. 状态变化：数据或状态的实际变更
4. 结果回传：返回值或副作用
5. 消费环节：谁在使用这个结果

避免只修单点而忽略链路上的其他环节。

### 区分问题来源

**规则**：区分问题的来源，避免混淆性质：

- 用户目标：用户真正想解决什么
- 现存缺陷：代码中已有的 bug
- 历史约定：为什么当初这样设计
- 验证发现：测试或检查暴露的问题
- 工具产出：lint、类型检查等工具的报告

## 逆推验证

### 从目标结果反推路径

**规则**：从目标结果或交付条件反推所需步骤、顺序和约束，验证当前路径是否成立。

**要求**：

- 先明确目标状态是什么样
- 再反推到达目标需要哪些步骤
- 验证当前方案是否覆盖了所有必要步骤

### 先明确不可变部分

**规则**：先明确哪些行为、结构和契约必须保持不变，再据此推导允许变动的边界。

**要求**：

- 列出不能改的：现有接口、公共类型、外部依赖、用户约定
- 列出可以改的：内部实现、私有方法、临时状态
- 不可变部分是硬约束，可变部分是优化空间

### 推导步骤依赖顺序

**规则**：多步骤任务先推导依赖顺序和最小执行单元，再安排执行。

**要求**：

- 识别哪些步骤可以并行，哪些必须串行
- 确保后续步骤不建立在未收敛的输入上
- 优先执行被依赖最多的步骤

### 修改前预判连锁影响

**规则**：在修改前预判对关联文件、派生内容和后续流程的联动影响。

**要求**：

- 修改接口定义时，检查所有调用方
- 修改数据结构时，检查所有消费方
- 修改配置项时，检查所有依赖该配置的流程
- 提前界定同步范围，不在事后发现遗漏

### 将契约放入统一框架推理

**规则**：把接口、类型、状态、数据和说明放进同一契约框架内推理。

**要求**：

- 接口定义、类型声明、状态管理、数据结构和文档说明应保持一致
- 任何一层的变更都要检查其他层是否需要同步
- 避免层与层之间口径分裂

### 逐项套用标准论证

**规则**：对候选方案逐项套用明确标准进行论证，而不是凭偏好或直觉判断。

**要求**：

- 评估标准：是否满足需求、是否最小改动、是否可回退、是否影响现有行为
- 每个方案都要过一遍标准，不跳过
- 记录不满足的项及原因

### 反向审视实现必要性

**规则**：从核心目标反推每项实现是否必要。

**要求**：

- 每个抽象、异常处理、兜底逻辑都要问：没有它会怎样？
- 如果去掉后不影响核心目标，就不加
- 压缩无效复杂度，不为假设性需求预留空间

### 调整结构时设计回退路径

**规则**：调整既有结构时同步设计：

- 保留路径：旧方式是否需要继续可用
- 替代路径：新方式的完整替代方案
- 回退条件：什么情况下需要回退
- 阶段验证点：每个阶段如何验证是否正确

避免一次性切换导致断裂。

### 反推不可跳过的步骤

**规则**：从强制约束和成功条件反推不可省略的步骤。

**要求**：

- 列出强制约束（用户要求、规范规定、工具限制）
- 从约束推导必须执行的检查、确认、同步和补救步骤
- 不可跳过的步骤必须显式执行，不能默认跳过
