# 文档精简

## 触发时机

- 文档行数超过 300 行预警线时
- 文档行数超过 500 行硬限制时
- 审查文档是否存在冗余内容时

## 精简策略优先级

按以下优先级依次执行，优先通过精简语言减少行数，其次才拆文件：

1. **删除重复内容**：同一信息在多处出现时，保留一处，其他改为引用
2. **删除冗余示例**：正反例只保留最典型的 1-2 个，删除"正确做法"的冗余示例
3. **合并同类条目**：多个类似条目合并为概括性表述
4. **简化表述**：长句改短句，删除修饰词和过渡语

## 具体精简手法

### 引用替代重复

当同一信息在多个文件中重复出现时，保留权威来源，其他位置改为引用。

**反例（重复内容）**：

```markdown
#### description 编写约束

- 遵循结构化公式：`<动词引导的动作>. <何时用 / 何时不用>.`
- "何时不用"是路由价值最高的信息...
- 只写技能用途...（详细展开 50 行）
```

**正例（引用）**：

```markdown
#### 编写约束

编写 SKILL.md 时需遵循以下约束，详细规范和示例见 `resources/skill-guide.md`：

- **description**：遵循结构化公式，控制在 2-3 句话
- **使用场景**：触发与排除条目必须贴近技能本质
```

### 删除冗余示例

正反例只保留最典型的 1-2 个，删除重复的变体示例。

**反例（多个正反例，30 行）**：

```markdown
**错误做法 1**——缺少负例：
（示例代码块）

**错误做法 2**——负例是"正确的废话"：
（示例代码块）

**错误做法 3**——负例引用其他技能名：
（示例代码块）

**正确做法**——贴近本质 + 保持独立：
（示例代码块）
```

**正例（一句话概括，3 行）**：

```markdown
**错误做法**：

- 缺少负例
- 负例是"正确的废话"（如"不用于造房子"）
- 负例引用其他技能名（如"使用 yy-edit-code"）

**正确做法**：负例必须是 AI 真实可能误触发的相邻场景，只描述行为差异，不点名其他技能。
```

### 条目合并

多个类似条目合并为概括性表述，减少重复。

**反例（多个独立条目，15 行）**：

```markdown
- [ ] 是否有必须询问用户才能继续的步骤？
- [ ] 默认策略是否覆盖 80% 以上的使用场景？
- [ ] 引导问题是否都是核心必要问题？
- [ ] 是否支持快速模式跳过确认？
- [ ] 每个选项是否都是"终点"？
```

**正例（合并核心项，5 行）**：

```markdown
- [ ] 默认策略是否覆盖 80% 以上的使用场景？
- [ ] 引导问题是否都是核心必要问题？
- [ ] 每个选项是否都是"终点"（选后直接完成动作）？
```

### 简化表述

长句改短句，删除修饰词和过渡语，保留核心信息。

**反例（冗长表述，8 行）**：

```markdown
**2. 阅读顺序等于执行顺序**

- 所有前置动作必须直接编入对应代码块的最前面，按真实执行顺序编号
- 不得用"代码块 + 后置补充说明"的形式追加前置步骤
- 写在代码块**之后**的解释段落不能改变前面已经发生的执行

错误示例（前置动作写在代码块后面，AI 顺序消费时会先执行 `git add`）：

（示例代码块）

正确示例：

（示例代码块）
```

**正例（精简表述，2 行）**：

```markdown
2. **阅读顺序等于执行顺序**：所有前置动作必须直接编入对应代码块的最前面，不得用"代码块 + 后置补充说明"的形式追加前置步骤
```

## 注意事项

- **保留核心要点**：精简时确保关键信息不丢失
- **引用要准确**：引用其他文件时，确保被引用文件包含完整信息
- **保持可读性**：精简后仍要保持逻辑清晰，不能过度压缩导致难以理解
- **行数约束**：单个文件不超过 500 行，超过 300 行时考虑是否需要拆分或精简
