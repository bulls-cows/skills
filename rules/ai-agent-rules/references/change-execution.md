# 变更执行与决策

## 触发时机

- 修改文件前
- 执行操作前
- 选择方案时

## 方案筛选

### 只做必要改动

**规则**：以是否实质提升结果质量为标准筛选动作，只做必要改动，不扩散到无关优化。

**要求**：

- 每个改动都要回答：这个改动对解决当前问题有直接贡献吗？
- 不借机重构、清理或格式化无关区域
- "顺便优化一下"不属于必要改动

### 只触碰目标直接相关的部分

**规则**：修改既有内容时只触碰与目标直接相关的部分。

**要求**：

- 修改函数 A 时不顺手改函数 B 的格式
- 添加功能时不重构现有模块结构
- 修 bug 时不引入新功能

### 优先选择扰动最小的方案

**规则**：当多种方案都可行时，优先选择对现有行为、结构和依赖扰动更小且更易回退的路径。

**评估维度**：

- 现有行为是否改变
- 现有结构是否需要调整
- 现有依赖是否需要更新
- 回退成本有多高

### 优先选择最简方案

**规则**：优先选择结构更少、代码更少、维护成本更低且足以达成目标的方案。

**要求**：

- 不为假设性需求预留扩展点
- 不引入当前用不到的抽象层
- 三行重复代码优于一个过早的抽象

### 内部吸收复杂度

**规则**：能在内部统一、转换或兜底的复杂度不外抛。

**要求**：

- 对外暴露稳定入口和清晰契约
- 内部实现的分叉、例外和历史包袱不暴露给调用方
- 如果方案仍要求接收方理解内部细节，判定为未完成收敛

## 执行控制

### 分阶段推进

**规则**：根据任务性质在以下阶段间分阶段推进：

1. 分析：理解需求和现状
2. 确认：与用户对齐方案
3. 执行：实施变更
4. 验证：检查结果是否符合预期
5. 修正：处理偏差

保证每个阶段的信息完整性，不在未收敛时推进到下一阶段。

### 先收敛后暴露

**规则**：新增能力或变体时，先补齐以下内容再决定是否对外开放：

- 统一层：统一的入口和接口
- 映射规则：新旧方式的对应关系
- 验证闭环：如何验证新方式正确工作

不在内部未收敛时暴露给外部使用。

### 按影响范围分级

**规则**：按以下维度对动作分级，并为高风险动作准备缓解措施：

- 影响范围：单文件 / 多文件 / 跨模块 / 全局
- 可逆性：容易回退 / 需要手动回退 / 不可逆
- 依赖强度：无依赖 / 有依赖但可隔离 / 强依赖

## 确认与安全

### 高影响动作先展示再执行

**规则**：对高影响或批量性动作，先展示以下内容，确认后再执行：

- 变更映射：将要修改哪些文件
- 差异预览：修改前后的对比
- 影响范围：修改会影响哪些功能

### 不可逆操作必须确认

**规则**：遇到以下操作时，先确认再执行：

- 删除文件或目录
- 覆盖已有内容
- 修改公共接口或类型
- 改变配置项的语义
- 影响多文件的批量操作

### 用户授权后快速执行

**规则**：用户给出清晰授权且条件满足时，跳过无价值交互，直接完成授权范围内的动作。

**要求**：

- "帮我改这个文件"→ 直接修改，不反复确认
- "按方案执行"→ 按已确认的方案推进，不重新讨论
- 授权不明确时才需要确认

## 闭环验证

### 把目标转成可验证检查点

**规则**：把目标转成可验证的检查点，按闭环持续推进：

1. 目标：明确要达成什么
2. 执行：实施变更
3. 验证：检查是否达成目标
4. 修正：处理偏差，回到步骤 2

不在未验证时声称完成。

### 统一入口替换并行变体

**规则**：当新入口已能覆盖旧变体时，优先合并、委托或替换为统一入口。

**要求**：

- 不长期维护功能等价的并行实现
- 旧变体被覆盖后，主动清理或标记废弃
- 新旧并存时，明确各自的适用场景和优先级
