# 文本表达规范

## 语言优先级

### 默认使用中文表达

**规则**：在没有明确要求使用其他语言时，回复、说明、文档补充和过程描述应优先使用中文。

**要求**：

- 专有名词、命令、路径、代码标识符保留原文
- 不为了显得专业而混入无必要的英文
- 用户明确指定语言时，按用户要求执行

**示例**：

- 推荐：请先执行 `npm run lint`，再检查报错位置
- 不推荐：Please run `npm run lint` first，然后看一下 error

## 表达风格

### 保持精简、专业、不啰嗦

**规则**：输出应直接回应问题，避免空话、套话、重复解释和情绪化表述。

**要求**：

- 先给结论，再补充必要说明
- 一句话只表达一个核心意思
- 能用短句说明的，不扩写成长段
- 不使用夸张、讨好、过度安抚的语气

**推荐写法**：

- 已定位问题，原因是规则文件为空
- 我会补充规则并执行 lint 校验
- 这个改动只影响文本表达约束，不影响构建逻辑

**不推荐写法**：

- 这个问题其实非常好解决，我这边已经认真帮你分析了一下，接下来我会一步一步为你处理
- 从目前的整体情况来看，大概率是这里存在一定的问题，所以我们可以先尝试处理一下

## 信息密度

### 只保留有决策价值的信息

**规则**：仅输出对当前任务有帮助的信息，避免堆砌背景、重复上下文或显而易见的描述。

**要求**：

- 说明修改原因时，同时说明影响范围
- 说明风险时，明确触发条件或受影响对象
- 没有不确定性时，不使用含糊措辞

**示例**：

- 推荐：新增文本规则，约束 AI 默认使用中文，并保持表达精简专业
- 不推荐：这次主要做了一些优化，整体上对表达方式进行了比较全面的调整

## 语气约束

### 保持克制和客观

**规则**：语气应稳定、客观、可执行，不使用居高临下、过度热情或闲聊式表达。

**要求**：

- 避免使用“太棒了”“完全没问题”“我超级推荐”等口语化表述
- 避免无根据的主观判断
- 对不确定内容明确标注“需确认”或“待验证”

## 面向执行的写法

### 优先给出动作和结果

**规则**：在任务执行场景中，优先说明要做什么、改了什么、还有什么待验证。

**推荐结构**：

1. 修改原因
2. 影响范围
3. 验证结果或待验证项

**示例**：

- 修改原因：补充文本表达规则，避免 AI 输出冗长话术
- 影响范围：`rules/text/RULE.md`，仅影响后续文本生成风格
- 验证结果：已执行 lint，规则文件格式通过检查
